# Чат на экране и голос: как подключить приложение к серверу

Документ для того, кто делает `android-app/`. Цель: **робот отвечает голосом на любой вопрос и дублирует
разговор на экране в виде чата**, а при прерывании ведёт себя предсказуемо. Форматы запросов — в
[`api-contract.md`](api-contract.md), здесь — порядок работы и правила поведения.

## Что есть на сервере

| Что нужно экрану | Эндпоинт | Статус |
|---|---|---|
| Ответ на вопрос, по фразам | `POST /v1/ask` с `Accept: text/event-stream` (SSE) | есть |
| Ответ на «Что это?» | `POST /v1/look` | есть |
| Голос посетителя → текст | `POST /v1/stt` | есть, OpenRouter (Gemini) |
| Голос → текст **по ходу речи** | `WS /v1/stt/stream` | **новый**, ElevenLabs Scribe Realtime; приложение уже подключено |
| Фраза → голос | `POST /v1/tts` | есть, ElevenLabs через OpenRouter, женские голоса RU/KZ/EN |
| Записать локальный ответ («где X», «проводи», «где я») | `POST /v1/sessions/{session_id}/messages` | **новый** |
| Восстановить чат | `GET /v1/sessions/{session_id}/messages` | **новый** |

Озвучка всех трёх языков через сервер включается без изменений кода: `VOICE_TTS_RU=server`, `VOICE_TTS_KK=server`,
`VOICE_TTS_EN=server` в `secrets.properties` или на экране диагностики.

## Модель чата на клиенте

Чат — это **локальный список сообщений** в `MainViewModel`. Сообщение появляется на экране сразу, сервер нужен
только для ответа и для истории. Сессия чата = `session_id`: новый id → пустой чат.

```kotlin
data class ChatMessage(
    val id: String,              // локально UUID; после ответа сервера можно сверять с "<request_id>:q|a"
    val role: Role,              // USER | ASSISTANT
    val text: String,            // у ответа растёт по мере прихода фраз
    val lang: Lang,
    val status: Status,          // см. ниже
)

enum class Status { THINKING, SPEAKING, DONE, INTERRUPTED, ERROR }
```

Состояния сообщения робота:

```
THINKING ──phrase──▶ SPEAKING ──последняя фраза доиграна──▶ DONE
    │                    │
    │                    └──новый вопрос / «Стоп»──▶ INTERRUPTED   (текст = только сказанное)
    └──новый вопрос / «Стоп»──▶ удалить пузырь или INTERRUPTED с пустым текстом
    └──ошибка сервера──▶ ERROR (текст = готовая фраза ошибки из приложения, она же озвучивается)
```

## Один вопрос от начала до конца

1. Посетитель спросил (голос → `/v1/stt`, кнопка или поле ввода). Добавить пузырь `USER` с текстом вопроса.
2. Добавить пузырь `ASSISTANT` со статусом `THINKING` (индикатор «думаю…»).
3. `IntentRouter` решает, кто отвечает:
   - **сервер** (`ask`, `look`) → шаг 4;
   - **робот сам** (`where_is`, `guide_to`, `where_am_i`) → показать и озвучить ответ, затем отправить его в
     `POST /v1/sessions/{session_id}/messages` (без ожидания результата; ошибку только залогировать).
4. `POST /v1/ask` с `Accept: text/event-stream`. На каждое событие `phrase`:
   - дописать `text` в пузырь робота, статус `SPEAKING`;
   - поставить фразу в очередь озвучки (`/v1/tts`, следующая фраза грузится, пока играет текущая — как в
     `ServerVoiceGateway.speakDetailed`).
5. `done` → больше фраз не будет; статус `DONE` ставится, когда **доиграла последняя фраза**, а не по `done`.
6. `error` или HTTP-ошибка → пузырь `ERROR`, текст и озвучка — готовая фраза из приложения (таблица «Ошибки»
   в контракте). Такие ответы сервер в историю не пишет.

Почему SSE, а не JSON: в SSE первая фраза приходит раньше, текст на экране появляется вместе с голосом, и сервер
видит, что посетитель перебил робота (ставит `interrupted: true` в истории). В JSON-режиме ответ приходит целиком,
и об обрыве озвучки сервер не узнает. Сейчас `RetrofitBackendApi` ходит в JSON — для чата его нужно перевести на SSE.

## Прерывания

Посетитель может перебить робота в любой момент. Правило одно: **новое действие посетителя важнее текущего ответа**.

| Что сделал посетитель | Когда | Что делает робот |
|---|---|---|
| Новый вопрос (голос, кнопка, ввод) | робот думает | отменить запрос (закрыть SSE), пузырь прошлого ответа убрать или пометить `INTERRUPTED`; начать новый вопрос |
| Новый вопрос | робот говорит | **сразу** остановить звук, отменить загрузку следующих фраз и SSE; прошлому ответу — `INTERRUPTED`, текст = только сказанные фразы; начать новый вопрос |
| «Стоп» | робот думает или говорит | то же, но нового вопроса нет; робот замолкает |
| «Стоп» | робот ведёт к точке | остановить навигацию, сказать «остановился» (как сейчас в `stop()`) |
| Та же кнопка ещё раз | ответ ещё готовится | игнорировать (защита от многократных нажатий, уже есть в `submit()`) |

Что уже делает текущий код: `submit()` и `stop()` вызывают `voice.stopSpeaking()` и `requestJob?.cancel()`;
`ServerVoiceGateway` останавливает `MediaPlayer` и отменяет предзагрузку следующей фразы. Для чата не хватает
только состояния пузырей: сейчас экран показывает один последний вопрос и ответ.

Что происходит на сервере: SSE-соединение закрыто до `done` → сервер перестаёт слушать модель и пишет в историю
вопрос и **уже отправленные** фразы с `interrupted: true`. Закрытие после `done` — обычный полный ответ.

Перебивание голосом, пока робот говорит, зависит от того, слышит ли микрофон самого робота. Без эхоподавления
робот распознает собственную речь как вопрос. Безопасный вариант для пилота: микрофон слушает только в паузах,
перебить можно кнопкой или касанием экрана.

## Live-распознавание (`WS /v1/stt/stream`)

**Уже сделано в приложении** (2026-10-22): `backend/LiveStt.kt` (OkHttp WebSocket), `MicRecorder.stream()`,
`ServerVoiceGateway.listenLive()`; если live не открылся (старый сервер, сеть) — минуту работает прежний путь
`MicRecorder` + `EnergyVad` → WAV → `/v1/stt`. Язык экрана передаётся с первой фразы. Как это устроено:

1. Нажали «Микрофон» (или робот слушает постоянно) → открыть WebSocket
   `…/v1/stt/stream?session_id=<id>&lang=<язык экрана>` с `Authorization: Bearer`.
2. Читать `AudioRecord` кадрами по 100 мс (3200 байт) и сразу слать бинарными кадрами — без накопления и без WAV.
3. `partial` → пузырь `USER` с текстом в реальном времени (серым/курсивом), текст заменяется целиком.
4. `final` → остановить запись, пузырь `USER` сделать обычным, `final.text` отправить в `/v1/ask`.
   Пустой `text` — молча вернуться в ожидание.
5. «Стоп» / новый вопрос кнопкой во время записи → `{"type": "cancel"}` и закрыть сокет.

Что это даёт: конец фразы находит сервер (VAD ElevenLabs, пауза 0,8 с), локальный `EnergyVad` больше не решает,
говорит ли посетитель, — уходит и проблема «на эмуляторе срабатывает через раз» (порог энергии в шумной
комнате). `{"type": "end"}` можно слать по кнопке «Готово» или по своему VAD, но это необязательно.

Если на сервере нет ключа ElevenLabs, `ready.provider` = `buffered:…`: протокол тот же, но `partial` нет, и фразу
нужно закрыть самому (`end` по своему VAD). Код клиента от этого не меняется.

OkHttp: `client.newWebSocket(Request.Builder().url(wsUrl).header("Authorization", "Bearer $token").build(), listener)`,
звук — `ws.send(ByteString.of(*bytes))`, команды — `ws.send("""{"type":"end"}""")`.

## Восстановление чата

`GET /v1/sessions/{session_id}/messages?limit=50` — когда экран пересоздан (поворот, процесс убит системой) и
локального списка нет. Сообщения приходят старые первыми, у каждого стабильный `id` (`<request_id>:q` / `:a`).
Заставка и таймаут бездействия создают новый `session_id` — чат на экране очищается, восстанавливать нечего.

## Пример: вопрос, перебитый новым вопросом

```
посетитель: «Какой пароль от Wi-Fi?»
  → USER «Какой пароль от Wi-Fi?»
  → ASSISTANT THINKING
  → POST /v1/ask (SSE)
  ← phrase «Гостевая сеть называется AstanaHub-Guest.»        → SPEAKING, звучит
посетитель нажимает «Во сколько работает хаб?», пока звучит первая фраза
  → звук остановлен, SSE закрыт
  → прошлый ASSISTANT: INTERRUPTED, текст «Гостевая сеть называется AstanaHub-Guest.»
  → USER «Во сколько работает хаб?», ASSISTANT THINKING, новый POST /v1/ask …

GET /v1/sessions/{id}/messages:
  user      ask  «Какой пароль от Wi-Fi?»
  assistant ask  «Гостевая сеть называется AstanaHub-Guest.»   interrupted: true
  user      ask  «Во сколько работает хаб?»
  assistant ask  «Хаб открыт …»                                interrupted: false
```

## Проверка вручную

```bash
T=<ROBOT_TOKEN>; S=$(uuidgen); U=http://10.0.2.2:8010/v1   # с ноутбука: http://localhost:8010/v1
curl -N $U/ask -H "Authorization: Bearer $T" -H 'Accept: text/event-stream' \
  -H 'Content-Type: application/json' -d "{\"question\":\"Где поесть?\",\"session_id\":\"$S\"}"
curl $U/sessions/$S/messages -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
  -d '{"kind":"where_is","question":"Где кафе?","answer":"Кафе справа от вас, метров 15.","lang":"ru"}'
curl $U/sessions/$S/messages -H "Authorization: Bearer $T"
```

## Готово, когда

- [ ] на любой вопрос робот отвечает голосом, и тот же текст появляется в чате;
- [x] микрофон работает через `WS /v1/stt/stream`: слова посетителя появляются на экране, пока он говорит;
- [ ] текст ответа растёт по фразам вместе с голосом;
- [ ] новый вопрос во время ответа останавливает звук мгновенно, прошлый ответ помечен «прервано»;
- [ ] «Стоп» останавливает звук и навигацию;
- [ ] локальные ответы («где X», «проводи», «где я») видны в `GET …/messages`;
- [ ] после пересоздания экрана чат восстанавливается из `GET …/messages`;
- [ ] заставка очищает чат.
